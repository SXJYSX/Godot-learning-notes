在 Godot 2D 开发中，提到“修改后会**延迟一帧生效**（或拿到旧数据）”的情况，最经典的主要是以下 4 个场景：

### 1. `RayCast2D` / `ShapeCast2D` 修改了坐标或方向（最经典 ⚠️）

- **现象**：在代码里修改了射线的 `position`、`target_position`，或者刚刚把 `enabled` 从 `false` 改为 `true`。
    
- **为什么延迟**： Godot 的射线检测默认是在**物理帧（Physics Step）结束时**才统一由物理引擎计算的。如果你在 `_physics_process` 中刚改了射线的方向，紧接着下一行直接调用 `is_colliding()`，**拿到的依然是修改前的检测结果（上一帧的物理状态）**。
    
- **解决办法**：修改属性后，**强行手动刷一行**：
    
    GDScript
    
    ```
    raycast.target_position.x = 50
    raycast.force_raycast_update() # ⚡ 强制物理引擎立刻刷新射线，消除 1 帧延迟！
    if raycast.is_colliding(): ...
    ```
    

### 2. `Area2D` 刚移动位置，或刚解禁 `CollisionShape2D.disabled`

- **现象**：刚刚把一个 `Area2D` 移动到新位置，或者刚刚把它的碰撞形状设为启用（`disabled = false`），紧接着在当帧调用 `area.get_overlapping_bodies()` 或 `get_overlapping_areas()`。
    
- **为什么延迟**：`Area2D` 的重叠列表是由 Godot 物理服务端（PhysicsServer2D）在物理管道刷新（Physics Flush）时维护的。在当前代码行，物理引擎还没来得及做空间相交计算，所以 `get_overlapping_bodies()` **在当前帧会返回空数组 `[]`**，必须等下一个物理帧才有数据。
    
- **解决办法**：被动等待 `area_entered` / `body_entered` 信号抛出，或者不要依赖当帧的 `get_overlapping_*` 强行轮询。
    

### 3. 使用 `set_deferred("disabled", ...)` 修改碰撞体状态

- **现象**：在处理受击或销毁逻辑时，为了防止 Godot 报错（“不能在物理刷新期间修改物理状态”），我们经常写：
    
    GDScript
    
    ```
    # 比如无敌帧生效，关闭 Hurtbox
    hurtbox_shape.set_deferred("disabled", true)
    ```
    
- **为什么延迟**：`set_deferred` 的本质就是“推迟到当前帧的物理计算结束（或下一帧开头）再赋值”。这意味着**在当帧剩下的代码执行过程中，这个 CollisionShape 依然是开启状态**，直到下一帧它才真正失效。
    

### 4. 场景树节点顺序造成的“逻辑延迟一帧”（竞态条件）

- **现象**：`Brain` 节点读取 `Sensors` 的数据做移动决策时，总是感觉 AI 反应慢半拍。
    
- **为什么延迟**：Godot 场景树在调用 `_physics_process` 时，是按节点树从上到下的顺序依次执行的。
    
    - 如果你的节点树是：`Brain` 在上，`Sensors` 在下。
        
    - `Brain` 先执行 `_physics_process` → 此时 `Sensors` 还没轮到执行当帧的检测 → **`Brain` 读取到的实际上是 `Sensors` 在上一个物理帧存下的旧数据**。
        
- **解决办法**：由顶级父节点（如 `Goblin.gd`）统一按顺序显式调用，彻底收回控制权（先 update传感器，再运行 Brain，最后运行状态机）。
