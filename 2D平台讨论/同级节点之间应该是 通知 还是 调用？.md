同级节点之间应该是 通知 还是 调用？

比如 heart通知level 自己被捡到了；level判定通关之后，

接下来 做法一：level直接调用 SceneService全局单例 的方法。比如change_scene()

做法二：level通知 EventsService全局单例，SceneService、UIService等其它“平级”的全局单例 监听EventsService的信号，依次做出响应

做法三：level通知 EventsService全局单例，EventsService信号激活后，依次调用SceneService、UIService等其它“平级”的全局单例的方法

---

同级节点之间**永远应该优先“通知（发射信号/事件）”，绝对避免直接“调用”**。

但在你提到的“通关后引发连锁反应（切场景、弹 UI、存档）”这个经典架构场景中，**做法三（配合“编排器/流水线”思想）是最佳解法，而做法二存在严重的工业级踩坑隐患。**

以下是对这三种做法的深度剖析与架构建议：

### 三种做法的本质区别与坑点

#### ❌ 做法一：`Level` 直接调用全局单例 `SceneService`

- **问题**：`Level`（玩法层）承担了不属于它的职责（流程控制）。
    
- **后果**：通关通常不是“立刻切场景”这么简单，往往伴随着：播放胜利音效 $\rightarrow$ 弹出 Victory UI $\rightarrow$ 异步保存游戏数据 $\rightarrow$ 淡出画面 $\rightarrow$ 真正切场景。如果写在 `Level` 里，`Level` 就会变成包含大量异步等待（`await`）的臃肿“万能节点”。
    

#### ⚠️ 做法二：`Level` 发信号，各全局单例广播监听、各自响应

- **问题**：**时序灾难与竞争条件（Race Conditions）**。
    
- **后果**：当 `EventsService` 广播 `level_cleared` 时，`UIService` 接收到信号开始播放 2 秒的胜利动画，但平级的 `SceneService` 也同时接收到了信号，并在第 1 帧就执行了 `change_scene()` 卸载当前场景——**UI 动画还没播完，场景就被直接切掉了！** 纯粹的广播事件无法保证跨系统的“严格执行顺序”。
    

#### ✅ 做法三（优化版）：`Level` 发信号，由“流程控制器/服务”统一顺序编排

- **优势**：**解耦了事件触发与流程编排**。
    
- **机制**：`Level` 只负责发出“我通关了”这个事实，不关心后续细节；由一个中枢（`CampaignService`）监听该事件，**以同步/异步流水线的方式，依次调用** `UIService` $\rightarrow$ `SaveService` $\rightarrow$ `SceneService`。

---

做法三的逻辑链条遵循 **“局部触发 $\rightarrow$ 关卡汇总 $\rightarrow$ 全局事件广播 $\rightarrow$ 中枢服务协程调度”** 的单向严格时序。

**1.1. 道具被拾取：**触发节点：Heart.gd (Leaf Node)。

- 玩家碰撞体进入 `Heart` 的 `Area2D`。
    
- `Heart` 不做业务逻辑判断，仅向上抛出本地信号 `heart_collected.emit()` 并执行 `queue_free()` 销毁自己。
    

**2.2. 关卡汇总与判定：**触发节点：Level.gd (Scene Root)。

- `Level` 节点监听了子节点 `Heart` 的本地信号。
    
- `Level` 更新内部计数器 `collected_count += 1`。
    
- `Level` 判定达到通关要求，向全局事件总线抛出事件：`EventBus.level_completed.emit()`。
    

**3.3. 全局事件总线转接：**触发节点：EventBus.gd (Autoload)。

- `EventBus` 纯粹充当无状态管道（Pipe），不包含任何判断，仅将 `level_completed` 信号广播给所有订阅者。
    

**4.4. 编排器捕获并按序调度：**核心节点：CampaignService.gd (Autoload Orchestrator)。

`CampaignService` 监听到 `EventBus` 的通关信号，通过 GDScript 的 `await` 协程按顺序指挥其他服务：

1. 调用 `InputService.set_input_enabled(false)`，立即封锁玩家操作。
    
2. 调用 `UIService.show_victory_banner()`，并 `await UIService.banner_finished`，暂停后续执行，等待通关 UI 动画播完。
    
3. 调用 `SaveService.save_game()`，并 `await SaveService.save_finished`，异步写入通关数据。
    
4. 调用 `SceneService.change_scene(next_scene_path)`，发起真正的切屏。
    

**5.5. 场景服务切屏与清理：**收尾节点：SceneService.gd (Autoload)。

- `SceneService` 播放黑屏淡出。
    
- 卸载老 `Level` 场景（老场景里的节点及本地信号自动从内存释放清理）。
    
- 加载并挂载新 `Level` 场景，播放黑屏淡入，恢复 `InputService` 操作。
    

### 核心调度代码实现

整个链条最关键的“中枢控制”集中在 `CampaignService.gd` 中，依靠 `await` 彻底消除并发竞争：

GDScript

```
# campaign_service.gd (流程编排器)
extends Node

func _ready() -> void:
	# 订阅全局总线事件
	EventBus.level_completed.connect(_on_level_completed)

func _on_level_completed() -> void:
	# 1. 禁用输入
	InputService.set_input_enabled(false)
	
	# 2. 播放胜利 UI 并阻塞等待 UI 播完
	await UIService.show_victory_screen()
	
	# 3. 异步保存，等待磁盘 I/O 结束
	await SaveService.save_progress_async()
	
	# 4. 前置准备无误后，最后执行场景切换
	SceneService.change_scene("res://scenes/levels/level_02.tscn")
```

这种设计的最大优势在于：**`UIService` 和 `SceneService` 依然完全平级且互不包含**，但由于引入了 `CampaignService` 这个“导演角色”，代码执行顺序变得绝对可控。
