在复杂的系统架构中，如果每一层的方法都叫 `hurt()`、`damage()` 或 `take_damage()`，很快就会产生“语义碰撞（Semantic Collision）”。三天下来看代码，根本分不清哪个方法负责物理判定，哪个负责血量扣减，哪个负责播放动画。

为了解决这个问题，优秀的架构设计会严格区分 **语义词根（Hit / Damage / Hurt）** 以及 **语法语态（主动指令 / 被动回调 / 事件广播）**。

如果是我来设计这套命名规范，我会遵循以下 **“三维分层命名法”**：

### 核心解耦理念：区分 Hit、Damage、Hurt

首先，在词汇选择上把这三个概念彻底拆开：

1. **`Hit`（击中/打击）**：**物理与碰撞层**。强调“物体碰撞到了”，此时还不知道对方会不会受伤（可能处于无敌状态）。
    
2. **`Damage`（伤害/数值）**：**规则与数值层**。强调“HP 改变、防具计算、无敌帧拦截”。
    
3. **`Hurt`（受击/状态）**：**表现与状态机层**。强调“播放受击动画、僵直、屏幕抖动、音效”。
    

### 🔄 完整数据流与命名对照表

我们将整个过程从头到尾的函数与信号重新命名：

| **阶段**         | **所在脚本**     | **类别**   | **推荐命名**                                | **命名逻辑与语义**                           |
| -------------- | ------------ | -------- | --------------------------------------- | ------------------------------------- |
| **1. 碰撞检测**    | `Hitbox.gd`  | 引擎回调     | `_on_area_entered(area)`                | Godot 原生碰撞信号回调                        |
| **2. 物理透传**    | `Hurtbox.gd` | 供外部调用的接口 | `receive_hit(hit_data)`                 | **Hit (打击)**：告知 Hurtbox“你被击中了”，传入打击数据 |
| **3. 中转广播**    | `Hurtbox.gd` | 抛出的信号    | `signal hit_received(hit_data)`         | **过去时**：表示“一次打击事件刚刚发生”                |
| **4. 信号监听**    | `Player.gd`  | 信号回调函数   | `_on_hurtbox_hit_received(...)`         | **`_on_来源_事件`**：Godot 官方推荐的回调命名规范     |
| **5. 数值结算**    | `Player.gd`  | 核心业务逻辑函数 | `apply_damage(amount)`                  | **Damage (数值)**：真正的扣血与无敌帧拦截计算         |
| **6. 物理表现**    | `Player.gd`  | 表现层函数    | `apply_knockback(force, dir)`           | **主动动词**：清晰表达此函数只负责受击击退               |
| **7. 状态变更**    | `Player.gd`  | 状态机调用    | `state_machine.transition_to("Hurt")`   | **Hurt (受击)**：指代受击僵直状态                |
| **8. UI/全局通知** | `Events.gd`  | 全局广播信号   | `signal player_health_changed(hp, max)` | **名词 + 状态**：通知 UI 刷新血条                |

### 💻 实际代码示例（看命名如何提升可读性）

#### 1. `Hitbox.gd`（碰撞层：只谈 Hit）

GDScript

```
func _on_area_entered(area: Area2D) -> void:
    if area is Hurtbox:
        # 语义：向 Hurtbox 传递一次物理“打击”
        area.receive_hit(damage, global_position)
```

#### 2. `Hurtbox.gd`（中转层：只谈 Hit）

GDScript

```
# 声明信号：打击已接收
signal hit_received(damage: int, attacker_pos: Vector2)

func receive_hit(damage: int, attacker_pos: Vector2) -> void:
    if not is_active:
        return
    # 抛出信号：我不处理逻辑，只通知 Player 我被 Hit 了
    hit_received.emit(damage, attacker_pos)
```

#### 3. `Player.gd`（逻辑层：区分 Listener、Damage、Hurt）

GDScript

```
func _ready() -> void:
    # 严格遵循 _on_节点名_信号名 的标准回调命名
    hurtbox.hit_received.connect(_on_hurtbox_hit_received)

# 1. 信号接收入口：只做调度，不写长逻辑
func _on_hurtbox_hit_received(damage: int, attacker_pos: Vector2) -> void:
    # 第一步：尝试施加数值伤害（内部会处理无敌帧拦截）
    var actual_damage = apply_damage(damage)
    
    # 如果实际伤害大于 0（说明没被无敌帧拦截）
    if actual_damage > 0:
        # 第二步：处理表现与状态
        apply_knockback(attacker_pos)
        trigger_invincibility_frames()
        state_machine.transition_to("Hurt") # 切入受击状态
        
        # 第三步：死亡判定
        if current_hp <= 0:
            handle_death()

# 2. 纯粹的数值扣减逻辑
func apply_damage(amount: int) -> int:
    if is_invincible:
        return 0
        
    current_hp = max(0, current_hp - amount)
    
    # 全局广播：玩家血量改变（通知 UI）
    Events.player_health_changed.emit(current_hp, max_hp)
    return amount

# 3. 纯粹的物理击退逻辑
func apply_knockback(attacker_pos: Vector2) -> void:
    var knockback_dir = (global_position - attacker_pos).normalized()
    velocity = knockback_dir * knockback_force
```

### 💡 总结：好的命名遵循的 3 个铁律

1. **绝不把业务逻辑全写在 `_on_xxx` 回调里**：`_on_...` 只做“接线员”，收到信号后去调用 `apply_damage()` 或 `apply_knockback()` 这种动词明确的函数。
    
2. **区分“动作”与“事件”**：
    
    - 函数（动作/指令）：用**动词 + 名词**，如 `receive_hit`、`apply_damage`、`trigger_i_frames`。
        
    - 信号（发生的事件）：用**过去时或状态描述**，如 `hit_received`、`health_changed`、`player_died`。
        
3. **词根明确分工**：
    
    - `Hit` = 碰撞/打击（Hurtbox / Hitbox 专属）
        
    - `Damage` = 血量/数值（Player 核心逻辑专属）
        
    - `Hurt` = 动画/僵直（状态机与表现专属）
        

这样拆分后，哪怕半年后再看代码，看到 `receive_hit` 就知道是碰撞接口，看到 `apply_damage` 就知道是扣血逻辑，看到 `Hurt` 状态就知道是受击动画，再也不会混淆！
